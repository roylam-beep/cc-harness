## 根因（由重到輕）

### 1. 把「blog 改稿上新站」理解成「整站搬家」（LLM 理解錯）
使用者整場只談 blog 內容與作者。「直做到 X 站去」最自然的讀法是**把這批改稿套到 X 站**，
不是把本機 Divi 舊站整包推過去。agent 沒有回頭對照「使用者要的成品是什麼」，直接沿用本機合併版
「整站重建」的思路。

### 2. 用 7 小時前的舊資訊判斷主機現況（LLM 沒刷新事實）
08:58 讀的 `ROCKET_SSH_HANDOVER.md` 寫「主機是剛建好的全新 WordPress」。之後 6 小時內，
另一個 session 已在主機上建好新站、並寫了 `HANDOVER.md`（14:14）與 `DEPLOY_PLAN.md`（14:52）。
agent 部署前沒重讀專案目錄的交接檔，也沒查 linked／同資料夾的其他 session。

### 3. 「唯讀檢查」漏掉唯一關鍵的三個問題
要整站覆蓋前，該問的是：**現在啟用哪個主題？有幾篇文章／頁？誰最近動過？**
15:01 的檢查一個都沒問；`wp-content` 的修改時間就是 15:01（有人正在動）也沒注意。
這三個查詢到 15:26 上傳完才跑。

### 4. dry-run 已經亮紅燈還照推
清單裡有 Divi 主題、Hide My WP 與 ManageWP 的自動載入外掛（`0-hidemywp.php`、`0-worker.php`）、
All-in-One Migration 備份資料夾——新站根本不用這些，自動載入外掛放上去就會執行。
agent 只把排除清單當「濾掉主機設定檔」用，沒把它當成「這東西該不該上去」的檢查。

### 5. 不可逆的遠端動作沒停下來問
計畫裡有「匯入資料庫並換網址」。使用者帳號層規則：對外、不可逆的動作要**當輪**明確授權，
而且授權範圍要跟動作對得上。「做到新站去」不等於「蓋掉新站的資料庫」。
有先做遠端備份是唯一救回來的原因。

### 6. 密鑰外洩
`grep -viE "PASSWORD|_KEY|_SALT"` 沒擋到 `CDN_SITE_TOKEN`，整串 token 進了 transcript，
agent 事後才告知。**該 token 應到主機面板重新產生**（本審查讀匯出檔時也再次經手，同樣算外洩一次）。

  給 24 篇媒體文加編按、改 `REDESIGN_REPORT.md`——使用者沒要這些（但本機、可逆，按帳號規則算可直接做，屬灰色）。

## 建議修法（未實作）

1. **harness**：`guard-bash.mjs` 加一類「遠端寫入」：`rsync`／`scp` 目的地含 `host:`、
   `ssh … 'wp db import|wp search-replace|rm '` → 要求使用者確認。（`BACKLOG.md` 已滿 12 條，沒加；收輪時再排。）
2. **規則**：部署到任何主機前，先回答三問並寫進回覆——啟用主題、文章／頁數、最近修改時間；
   再讀專案根目錄所有 `*HANDOVER*.md`、`DEPLOY_PLAN.md`。專案層 memory 已有一條
   `check-remote-before-deploy.md`（該 session 事後自己寫的），但它只在那個專案生效。
3. **密鑰**：讀 `wp-config.php` 一律用白名單（只 grep `DB_NAME|table_prefix|WP_HOME|WP_SITEURL`），
   不用黑名單。
