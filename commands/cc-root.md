追根 $ARGUMENTS。沒指定就追本次對話中最近一個尚未拍板的修法。

**你的工作是找出「為什麼長得出這個 bug」，不是修這個 bug。** 手上現成的修法只是候選之一，不是起點。

## 流程

### 1. 寫不變量

一句話寫「什麼必須一直成立」。**主詞不能是檔案、hook、步驟或指令**——那些是手段，不是目標。

- 壞：「`.git/hooks/pre-commit` 要存在」「agent 要記得 `git add -f`」
- 好：「agent 每次 commit 之前都跑過快閘」「harness 標準件一定進版控」

### 2. 找同根症狀

搜 `BACKLOG.md`、`docs/decisions.md`、`handovers/`、`git log --oneline -50`、出事那個檔的 `git log`。
列出看起來無關、但指向同一個上游的症狀。只找到一個就寫「單點，未見同根」，**不要硬湊**。

### 3. 往上問到設計決定

從症狀往上問「為什麼會這樣」，每一環一行，附證據（`路徑:行` 或指令輸出）。
停點是一個**設計決定**：誰、在哪一層、選了什麼做法。
停在「漏了一步／忘了做／agent 沒想到」＝還沒到底，接著問「為什麼漏得掉」。

### 4. 派對抗（預設開）

**同一則訊息**平行開 3 個 Agent，`subagent_type: Plan`（它的工具集沒有 Write／Edit，天生唯讀），
互相看不到彼此。每個 prompt 逐字包含：

```
你在 <repo 絕對路徑>，唯讀，不改檔、不 commit。
不變量：<第 1 步>
因果鏈：<第 3 步，每環一行＋證據>
同根症狀：<第 2 步>
現成修法（不要重提它）：<原修法一句>
你的鏡頭：<下面三選一，只給這一個>
只回五行：修法一句／層次 L0–L3／改動面（幾個檔、哪幾個）／致命前提（不成立就整個垮的那一條）／驗它的一條唯讀指令。
提不出符合鏡頭的修法就直說，不要湊。
```

- **A 平台原生**：這件事平台（git、Claude Code、CI、OS、框架）本來有沒有機制在做？用它取代自造的。
- **B 拿掉**：假設這個功能／步驟／檔案不存在，不變量還能不能靠別的東西保住？
  修法一句必須以「拿掉 <某個現有的東西>」開頭——什麼都沒拿掉就是換層，不是這個鏡頭。
- **C 換層**：把保證搬到另一層（CI、伺服器端、型別、資料結構、安裝方式），讓這類 bug 根本不可能發生。

三個回來後，收斂到同一解的合併成一個候選，並在輸出標「N 個鏡頭收斂」（信心訊號，不是失敗）。
主 agent 把現成修法和自己想得到的 L0／L1 補進候選，再開 **1 個紅隊 Agent**（`Plan`），prompt 給全部候選，要它對每一個：

1. 跑該候選的致命前提驗證指令（只跑唯讀的；要寫檔才驗得了的標「待驗」）。
2. 給最強一條反對意見，格式：`<一句反對>。會怎麼壞：<情境＋後果>。<證據>`。
3. 判 `活`／`死`／`待驗`。**不准提新方案**。

主 agent 只當裁判，不改寫候選來救它。
Agent 工具叫不起來時，主 agent 依序套三個鏡頭自己做，輸出第一行標「未對抗（單一 agent）」。

### 5. 分層次

| 層次 | 意思 |
|---|---|
| L0 補症狀 | 只讓這次的症狀消失：補一行、加個提醒、補裝一次 |
| L1 修機制 | 同一個機制不會再出這種錯 |
| L2 換位置／換方案 | 保證搬到別的層，或換掉做法 |
| L3 改目標／拿掉 | 不變量本身改寫，或功能整個不要 |

候選至少要有一個 L2、一個 L3。真的湊不出，寫出為什麼——這本身就是結論。

## 輸出（就這五段）

1. **不變量**：一句。
2. **根因**：一句，後面接因果鏈（每環一行附證據）與同根症狀。
3. **候選**：一條一行，層次高的在前。
   `<L?> <修法一句>。改動：<N 檔>。紅隊：活／死（<反對一句>）／待驗（<指令>）`
4. **推薦**：只給一個，標層次。
   - 推薦 L0／L1 → 必須寫「為什麼 L2 以上不值得」。沒寫就是不合格的輸出。
   - 明知是治標還選它 → 寫「知情治標」，附一行 `BACKLOG.md` 草稿記下根因（本支不寫檔）。
   - 候選全被判死 → 推薦「先驗證」，指名要驗哪一個待驗前提。
5. **動手前先驗**：一條指令，驗推薦方案的致命前提。

## 規矩

- **唯讀。** 不改檔、不 commit、不實作；子 agent 也一樣。
- 事實一律以指令輸出或 `路徑:行` 為準，查不到標 `[需確認]`。
- 紅隊判「死」的候選不能推薦。
- **不為深而深。** 深層方案的成本比問題本身還大時，選低層次是合法的，但理由要寫出來。
- 跟不變量無關的發現，只在輸出最後加一行「範圍外：…」，不展開。
- 跟 `/cc-grill` 的分工：grill 訪談使用者，問清楚要的是什麼；本支找根因、推翻方案。
  使用者的目標還沒講清楚就先跑 `/cc-grill`，把不變量問出來再回來。

## 防什麼

修法錨定在症狀上：目標被寫成「某個檔要存在」「agent 要記得做某步」，每次只補當下那個洞；
深層方案一被反駁就退回治標，同一個根因換個樣子再長出來。
